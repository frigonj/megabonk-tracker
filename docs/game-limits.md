# Game limits and caps

A working reference of every hard limit, cap, or ceiling found in Megabonk that's relevant to build optimization — compiled from `docs/wiki-reference/` (community wiki snapshot, 2026-08-17) and cross-checked against decompiled game source where noted. Update this file as new limits are confirmed or corrected.

**Status key:** ✅ confirmed (wiki + decompile agree, or decompile alone) · 📖 wiki only (not independently verified against source) · ❓ open question — needs a live test.

## Weapon and tome levels

- ✅ **`IUpgradable.GetMaxLevel()`** is a real per-weapon/per-tome method (`WeaponData`, `TomeData` each override it independently) — confirmed via decompile of `Assembly-CSharp.dll`. The actual numeric return value is compiled into native IL2CPP code and isn't visible from a managed decompile; plugin instrumentation to log the real value per weapon/tome was written 2026-08-19 but isn't deployed yet (see `gaps-scoped.md` #gap-013).
- 📖 **Weapons cap at level 40 by default** ("the standard level-40 cap," per the Wizard's Hat item description). This directly contradicts the user's earlier recollection of a level-50 weapon cap — **needs resolving against the live `GetMaxLevel()` capture once #gap-013 deploys**, don't trust either number until then.
- 📖 **Stainless Steel Pot** (item) raises a *weapon's* level cap beyond the standard 40, for one specific weapon per copy. Unlock: play as Vlad, use it to upgrade a weapon beyond the standard cap.
- 📖 **Wizard's Hat** (item) does the same for **tomes** ("functions like the Stainless Steel Pot but for Tomes").
- 📖 A "level 9999 exploit via weapon/tome banishing combinations" was patched out (Hotfix v1.0.69) — banish/refresh loops that bypassed level caps are **no longer viable** in the current build. Relevant since the user's best run (55) used 4 banishes/7 refreshes; that's normal reroll behavior, not a cap-bypass exploit, under the current patch.
- ✅ **Tomes cap at level 99** — confirmed directly: `docs/wiki-reference/tomes.md` line 10 states "Each tome upgrades up to Level 99," corroborating the user's original recollection. (Missed on first pass through the wiki snapshot — found on a second, more targeted search.) Per-level effect magnitude scales with the rarity tier of the upgrade offered (Common→Legendary), not a flat per-level amount.

## Player stats

- 📖 **Armor**: percentage damage reduction, additive with diminishing returns, practical cap **~94%** (cannot reach 100%).
- 📖 **Evasion**: percentage chance to fully avoid damage, additive with diminishing returns, practical cap **~94%**. Ninja's execute mechanic is built around this stat specifically.
- ✅ **XP Gain multiplier is capped at 10x for actual XP awarded** — confirmed via decompile: `Inventory__Items__Pickups.Xp_and_Levels.PlayerXp` has a distinct static `maxXpMultiplier` field, separate from the `XpIncreaseMultiplier` `EStat` the plugin tracks. `PlayerXp.AddXp(int)` is the real XP-award method; `maxXpMultiplier` is almost certainly what clamps its effective multiplier to 10x, consistent with both the wiki and the user's in-game experience. **Critical caveat, confirmed empirically 2026-08-19**: the tracker's `XpIncreaseMultiplier` stat (visible in `player_stats_snapshot` / the dashboard's Player Stats table) is the raw, *uncapped* accumulated value from every XP-Gain source (tomes, passives, items) — it does NOT reflect the clamp. In run 64 it climbed steadily to 32.8 with zero plateau across a 1634s run, while actual awarded XP was almost certainly clamped at 10x that entire time. **Do not use the tracked `XpIncreaseMultiplier` number to judge whether more XP-Gain investment is worthwhile — it will always look like it's still climbing even long after it stopped mattering.** See gaps-scoped.md for the fix (surface `maxXpMultiplier` / an effective-vs-raw distinction in the dashboard).
- 📖 **Max HP**: no stated cap — grows via items (Oats, Demonic Blood), the HP Tome, and +1 per character level (since v1.0.17). One weapon (Bananarang, per `weapons.md`) has an explicitly **uncapped** +1 Max HP on kill chance.

## Luck — no evidence of a hard threshold, likely a smooth continuous curve

The user asked (2026-08-20) whether there's a Luck threshold that significantly impacts item/weapon rarity. Investigated via decompile + this project's own run data rather than guessing:

- ✅ **Every rarity roll takes Luck as a continuous `float` input, not a boolean/threshold check.** Decompiled `Assets.Scripts.Inventory__Items__Pickups.Rarity` (confirmed real): `GetUpgradeOfferRarity(float luck)`, `GetEncounterOfferRarity(float luck)`, `GetItemRarity(float luck)`, `GetShadyGuyRarity(float luck, ...)`, and `CalculateRarityWeights(float[] weights, float luck)` all take `luck` directly into what looks like a weighted-roll calculation, not a step function. This is reasonably strong evidence **against** a hard cliff-edge threshold existing at all — the method shapes look like Luck smoothly shifts the rarity-tier weights as it rises, not "nothing happens below X, then a jump."
- ✅📊 **Checked directly against run 64's own data (245 picks, Luck ranging 0.33 → 0.79 across the run) and found no clean threshold** — bucketing picks by the player's Luck value at time of pick shows rarity odds shifting noisily as Luck rises (e.g. Legendary picks appear at both low-Luck and high-Luck buckets, Common% doesn't monotonically fall), consistent with a smooth continuous curve rather than a breakpoint, but the sample is too small per bucket (12-116 picks) to fit a real curve or rule out a subtle threshold entirely.
- ❓ **Not the same thing as weapon/tome level** — this is worth being precise about since the question could be read either way: Luck affects the **rarity of the offer** (Common→Legendary), not how many levels a pick grants directly. Rarity in turn determines the *magnitude* of that pick's stat bonus (confirmed in `weapons.md`'s per-weapon upgrade tables, e.g. one weapon's Damage bonus is 2.5/3/3.5/4/5 across Common→Legendary) — so Luck's real effect on "weapon levels" is indirect: it doesn't make you level up faster, it makes each level-up worth more.
- **Practical takeaway**: no known amount of Luck is confirmed to unlock qualitatively different behavior. Investing in Luck looks like a smooth, diminishing-but-continuous return, not a target to "hit a threshold" and stop. If a real breakpoint exists, it wasn't found in either the decompiled method signatures or this run's empirical spread — would need either a much larger multi-run dataset (correlating Luck value against rarity-roll outcome, same method as above but pooled across many runs) or the native method body (not accessible via managed decompile) to rule it out definitively.

### Diminishing returns — weak but real signal, low confidence (only 3 usable runs exist)

Follow-up question (2026-08-20): is there a point where leveling Luck gives diminishing returns? Checked across all 3 currently-completed runs (34, 55, 64 — the only ones with real data as of this pass; run 35, initially suspected as a comparison point, turned out to be a near-empty #gap-010 fragment with only 4 picks and no usable Luck data).

Per-run average rarity value (Common=0…Legendary=4, weighted by pick count) against each run's average Luck at time of pick:

| Run | Picks | Avg Luck at pick | Avg rarity value | Final Luck |
|---|---|---|---|---|
| 64 | 245 | 0.43 | 1.25 | 0.81 |
| 34 | 45 | 2.14 | 1.40 | 2.88 |
| 55 | 44 | 2.21 | 1.71 | 2.71 |

- **The pattern is consistent with diminishing returns setting in early**: going from run 64's ~0.43 average Luck to runs 34/55's ~2.1-2.2 (roughly a 5x increase) only moved average rarity value from ~1.25 to ~1.4-1.7 — nowhere near a proportional 5x improvement. Pooling all 334 (Luck, rarity) pairs across all three runs into quantile bins shows the same shape: rarity value jumps sharply in the very lowest Luck bucket (0.33→0.34), then stays roughly flat (1.2-1.5) across every bucket from ~0.34 all the way up to 2.88 — suggesting most of Luck's benefit is realized early, with comparatively little gained pushing it much higher.
- **Confidence is low — flagging this honestly rather than overstating it**: n=3 runs total, and runs 34/55/64 differ in more than just Luck (different characters/builds/durations/difficulty growth), so this can't cleanly isolate Luck's effect from those confounds. It's a real observed pattern in this project's own data, consistent with what a saturating rarity-weight formula would produce, but not a rigorously controlled result. Revisit once more level-50+ runs accumulate — the same query (bin all picks across all completed runs by Luck-at-pick-time, compare average rarity value) gets more reliable as the sample grows.

## Item-specific caps (examples — not exhaustive, see `docs/wiki-reference/items.md` for the full 85-item list)

- **Leeching Crystal** (or similarly-named +HP-per-kill item): +0.5 Max HP per kill, capped at **200 stacks** (+100 Max HP total).
- **Calcium's scaling item** (+0.1% Damage per kill): capped at **+100%** total.
- **Crit-explosion item**: explosion radius capped at **8m** (base 4m, scales with Size/copies).
- **Dexecutioner's Execute item**: each Execute grants +1% Damage permanently, but **capped at 200 Executes/minute**.
- **Za Warudo**: capped at **25 max per run** (patch-added cap).
- **Joe's Dagger**: damage growth capped at **200/minute × number of daggers owned**.
- **Cursed Grabbies**: proc-per-tick limit, capped at **250**.
- **HP Regen**: capped at **1-per-tick** (patch fix, prevents a stacking exploit).

These are illustrative of the *pattern* (many items have per-run or per-minute caps to prevent runaway scaling) — a full audit of all 85 items' individual caps wasn't done here; check `docs/wiki-reference/items.md` directly for a specific item.

## Run structure

- 📖 Each map (Forest, Desert) has **3 sequential Tiers**, each ending in a boss fight that spawns a teleporter to the next tier. Slums (Calcium's map) is a single 16-minute, 2-stage format instead.
- 📖 Mini-bosses spawn once per run at fixed timers (7:00 or 2:00 remaining, or 6:30/1:30 at Tier 3).
- ✅ **The run timer is 10 minutes, and hitting 0 triggers Final Swarm — but Final Swarm is a survivable escalation, not a forced run-end.** Confirmed by the user (2026-08-19). This resolves the apparent contradiction with this project's own data: run 55 (858s / ~14.3 min) and run 64 (1634s / ~27 min) both ran well past the 10-minute mark and both ended in a real death (`outcome: died`), not a timer cutoff — because the timer hitting 0 starts Final Swarm rather than ending the run. A build strong enough to survive Final Swarm just keeps playing indefinitely from there, fighting through escalated difficulty (and, per the other trigger, killing every boss also starts it — so a very fast, thorough clear could hit Final Swarm before 10 minutes are even up). **This reframes "survive as long as possible" concretely**: the first ~10 minutes (or faster, if bosses are cleared quicker) is the "normal" phase, and everything past that is Final Swarm — the run's real skill/build ceiling is how long you can last *inside* Final Swarm, not whether you reach it. Exact in-Final-Swarm behavior (spawn rate, enemy stat multipliers, whether it keeps escalating further over time) is still unconfirmed — see #gap-016 for the plan to log the transition and observe it directly.
- ✅ **There is a real "Final Swarm" state, and its trigger is now confirmed** — `Assets.Scripts.Managers.EnemyManager.IsFinalSwarm()` is a real, callable method (confirmed via decompile). Per the user (2026-08-19): the Final Swarm triggers **after killing every boss, or once the run timer hits 0** — whichever comes first. This resolves the earlier open question about what happens post-Tier-3: the wiki's silence wasn't because nothing happens, it's an undocumented distinct endgame state with two independent triggers (boss-clear completion, or a hard time limit). The exact in-swarm behavior (harder spawns? every remaining enemy at once? a fixed duration?) is still unconfirmed — worth observing directly next time a run reaches it, or having the plugin poll `IsFinalSwarm()` and log the moment it flips true (see #gap-016) to capture the transition precisely.
- 📖 **CC-cap system**: after 20 minutes into a run, enemy (ghost-type) speed increases and player stun/freeze immunity threshold gradually lowers — a deliberate late-run difficulty ramp independent of enemy HP/damage scaling.

## Quiet mechanics found in code, not documented on the wiki (2026-08-19 pass)

Found by decompiling `EnemyManager`, `WeaponInventory`, `TomeInventory`, and `UpgradePicker` looking specifically for cap/limit-shaped methods and fields the wiki doesn't mention. None of these have their exact numeric values confirmed (IL2CPP method bodies aren't visible to a managed decompile) — they're confirmed to **exist**, not yet confirmed **how strict** they are.

- ✅ **There's a hard concurrent-enemy cap**: `EnemyManager.HasMaxEnemies()` / `GetNumMaxEnemies()` are real methods — enemy density does NOT scale infinitely with `Difficulty`/`EnemyAmountMultiplier`. Past this cap, the game almost certainly compensates by scaling individual enemies harder (HP/damage) rather than spawning more, since `EnemyHpMultiplier`/`EnemyDamageMultiplier` are separate tracked stats. This matters directly for the DPS-vs-enemy-HP tracking added tonight (`enemy_health_history`) — a build hitting the enemy cap should show total-enemy-HP growth slow down even as `Difficulty` keeps climbing, which would be visible in that data once a few more runs exist.
- ✅ **`WeaponInventory.isMaxed` / `TomeInventory.isMaxed`** — both inventories expose a direct "is this inventory full" boolean, and `IsMaxLevel(EWeapon)` / `IsMaxLevel(ETome)` let the game (and in principle the plugin) check per-weapon/per-tome cap status directly, without inferring it from level numbers. This is the actual mechanism behind the "find weapons/tomes in level-ups until slots are full, then level what you have" flow described earlier — it's not implicit, the game tracks it as an explicit state. **Not currently read by the plugin** — could be captured cheaply alongside the existing weapon/tome level polling, giving the tracker a direct "still finding" vs. "fully committed, now leveling" run-phase signal instead of inferring it from pick names.
- ✅ **Banishing has a cooldown, gated per-use, not just per-level-up-screen** — `UpgradePicker` has a full trio: `banishMode` (a get/set bool property, not just a backing field — `StartBanishMode()` / `Banish()` / `StopBanishMode()` are all separate real methods), plus `banishCooldownOverAtTime`. The field is an absolute timestamp (`Time.time`-style), not a fixed duration constant, so the exact cooldown length in seconds isn't visible from the decompile — but its existence confirms banishing is throttled per-use, not just limited by how many level-ups you get. Not mentioned anywhere in the wiki snapshot. Relevant to both run 55 (4 banishes) and run 64 (5 banishes) — you likely couldn't have banished meaningfully faster even by clicking faster.
- ✅ **Moai shrine grants items directly, with a distinct integer-typed luck mode — not a simple stat-boost shrine at all.** `Assets.Scripts.Inventory__Items__Pickups.InventoryUtility.GetRandomItemsMoai(int moaiLuckMode)` is the real underlying method (confirmed via decompile) that `UpgradePicker.SetMoaiLuck(int)` feeds into. Two things this clarifies beyond last night's finding: (1) Moai's reward is an **item grant**, mechanically closer to a chest/shop-offer roll than the stat-modifier effects the plugin's `EffectSource` tracking (`#gap-004`) currently expects from shrines — meaning Moai rewards likely do **not** currently show up in the tracker's `effects_applied` event stream at all, since that path is wired to `EffectStat.ApplyEffect`, a different mechanism; (2) `moaiLuckMode` being an **int, not a bool**, means there are likely multiple distinct luck tiers/modes, not just "on." The wiki snapshot has **zero mentions of "Moai" anywhere**, despite `InteractableShrineMoai` existing as a real class. Given the item-grant mechanism, `#gap-004`'s existing plan (watch for `effect_applied` events) likely needs revising to also watch for `upgrade_picked`/item-related events around a Moai interaction instead.
- ✅ **Shady Guy is a second, entirely separate undocumented mechanic, also item-grant-based** — `InventoryUtility.GetRandomItemsShadyGuy(EItemRarity itemRarity)` is real, and `UpgradePicker` has a matching `A_ShadyGuyDone` static `Action` event. Rarity-filtered (unlike Moai's plain int mode), suggesting Shady Guy offers a rarity-guaranteed item pick. Not in the wiki snapshot, not currently tracked by the plugin at all — found only because it sits next to `GetRandomItemsMoai` in the same utility class. Worth the same live-observation treatment as Moai next time either appears in a run.
- ✅ **The weapon/tome level cap has an explicit base-plus-bonus structure, not one flat number** — `InventoryUtility` exposes `MAX_WEAPON_LEVEL_BASE` / `MAX_TOME_LEVEL_BASE` (the base 40/99 figures) as real static fields, separately from `GetWeaponMaxLevel()` / `GetTomeMaxLevel()` (the effective, possibly-boosted cap) and `GetNumExtraWeaponLevels()` / `GetNumExtraTomeLevels()` (how much extra is currently granted, e.g. from Stainless Steel Pot / Wizard's Hat). This is a complete, precise confirmation of the base-cap-plus-item-bonus model — and all four values are cheaply readable live via the plugin, resolving the open 40-vs-50/99 question definitively without waiting on `#gap-013`'s `IUpgradable.GetMaxLevel()` route.
- ✅ **Weapon/tome slot counts are separately queryable from "is it full"** — `InventoryUtility.GetNumAvailableWeaponSlots()` / `GetNumMaxWeaponSlots()` (and the tome equivalents) give the actual current/max slot counts as integers, a more precise signal than `WeaponInventory.isMaxed`/`TomeInventory.isMaxed`'s plain booleans (found in last night's pass). `CanUnlockWeapons()` / `CanUnlockTomes()` / `CanUnlockItem(IUpgradable)` are also real — likely what actually gates whether "new weapon/tome" picks are still possible to offer, independent of slot count (e.g. once every weapon in the loot pool is already owned).

## Difficulty / enemy scaling

- The `Difficulty` stat (tracked live by the plugin, visible in `player_stats_snapshot`) increases enemy count, HP, damage, and speed, and rises from both natural progression and specific sources (Shrine of Greed reliably adds +0.05 per use, confirmed from live event data across multiple runs). It does **not** affect XP drop rate, only spawn rate.
- No explicit ceiling on `Difficulty` found in the wiki. The DPS-vs-enemy-HP tracking added 2026-08-19 (`enemy_health_history` table, pending deploy per #gap-013) is meant to make this scaling directly visible per-run rather than inferred from patch notes.

## What this means for optimization (tying back to the project's stated goal)

- Weapon cap is 40 by default (tomes cap at 99); as of run 64 the tracker has now seen weapon levels well past 16 (LightningStaff hit 40, the exact wiki-documented cap) — so the earlier "runs never approach the cap" read no longer holds once a run reaches the length/scale run 64 did. Worth re-checking weapon caps directly once #gap-013's `GetMaxLevel()` capture deploys.
- **XP Tome / XP-Gain investment past the 10x effective cap is very likely wasted, and run 64 is direct evidence of it**: `XpIncreaseMultiplier` was already at 10.7 (over cap) at the very first snapshot and kept being fed by 22 more XP Tome picks across the run, reaching 32.8 raw — all of that investment beyond the point the *effective, clamped* multiplier hit 10x contributed nothing to actual leveling speed. Every character is XP-capped at 10x (not just Spaceman), per the user (2026-08-19) — so this isn't a character-choice problem, it's a "stop picking XP Tome once you're near the cap" problem. The catch: the dashboard currently can't tell you when you've crossed the *effective* cap, because it only shows the raw uncapped stat (see the XP Gain entry above) — this needs fixing before the tracker can reliably flag "stop picking XP Tome now."
- Armor/Evasion diminishing returns mean over-investing past ~94% wastes picks that could go toward damage/attack-speed scaling instead — worth flagging if a build's player-stats snapshot shows Armor or Evasion pushed unusually high.
- Per-item/per-minute caps (Za Warudo, Joe's Dagger, Cursed Grabbies, etc.) mean stacking certain items past their cap is a wasted pick — the tracker's pick data could flag this directly (a build taking 6+ copies of a 5-copy-max item) but doesn't currently check picks against known item caps.
