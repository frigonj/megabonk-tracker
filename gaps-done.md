## Live verification (2026-08-17)

- [x] `upgrade_picked`, `player_stats_snapshot`, `damage_snapshot` events confirmed working end-to-end against a live game run  [plugin/dashboard] — deployed and tested; found and fixed two real bugs blocking them: (1) `WeaponData.GetBaseStat(EStat)` throwing `KeyNotFoundException` for undefined stats crashed the entire poll tick every frame, (2) `SelectUpgrade`'s postfix threw `IndexOutOfRangeException` iterating the Il2Cpp `upgradeOffer` list via `foreach`, silently dropping every pick after the first. Fixed with per-stat try/catch in `ReadStats` and indexed access instead of `foreach`. See commit 8721535.  #gap-001
- [x] Live in-game stutter caused by polling all 57 `EStat` values against every weapon + player every second  [plugin] — root cause: the exception-catching added for gap-001 turned an already-expensive 57-stat walk into repeated caught exceptions per tick (undefined stats throw by design in the game's own code). Fix: stopped polling weapon/player stats live entirely — they're now captured once at `OnDied`, since the build-analysis use case only needs end-of-run values. Damage and run counters stay on the live 1s poll (cheap reads, not the bottleneck). Superseded by the valid-key-caching fix that restored live polling without the exception cost — see the 2026-08-17 entry below and `project_megabonk_tracker.md` memory. See commit 2c7c328.  #gap-006-superseded

## Pause detection + stutter regression (2026-08-18)

- [x] Pause detection (`PauseUi.Pause`/`Resume`, `DamagePoller.IsPaused`, `tracker.py`'s `elapsed_seconds`/`total_paused_seconds`) verified against a real live pause/resume cycle, not just synthetic timestamps  [plugin/dashboard] — a real `game_paused`→`game_resumed` cycle occurred in a live run (`00:19:00`→`00:19:15`), confirmed via `performance_snapshot` and event log data that timing/duration tracking behaved correctly. Previously only unit-tested.  #gap-005
- [x] Stutter regression reported as "every tick" after adding live FPS telemetry  [plugin] — root cause found via the new `performance_snapshot` data itself: `EventSink.Emit` opened, wrote, and closed the NDJSON file on every single call, and the 1s poll tick calls it 4-5 times back to back (damage, run counters, weapon stats, player stats, performance) — real per-tick file-handle churn on the Unity main thread, worst on the tick that also handled a pause-menu resume. Confirmed via live data: before the fix, `minFps` collapsed from ~35 to ~9 immediately after `game_resumed` and never recovered for 20+ seconds; after the fix (persistent `FileStream` opened once, `ResetForNewRun` truncates in place instead of reopening), the same pause/resume cycle showed only one transient dip before immediately recovering to the pre-pause baseline (`minFps` back to 90-125 within 2 samples). Fix: rewrote `plugin/EventSink.cs` to hold an open `FileStream` for the plugin's lifetime instead of `File.AppendAllText`/`File.WriteAllText` per call.  #gap-009

## XP cap display bug (2026-08-19)

- [x] Dashboard's tracked `XpIncreaseMultiplier` was the raw uncapped stat sum, not the actual effective XP multiplier the game applies — it climbed forever with no plateau (32.8 in run 64, still rising at run end) while the real in-game XP gain is clamped at 10x, misleading anyone judging whether more XP-Gain investment (XP Tome, etc.) was still worthwhile  [plugin/dashboard] — root cause confirmed via decompile: `Inventory__Items__Pickups.Xp_and_Levels.PlayerXp.maxXpMultiplier` is a separate public static field holding the real clamp value, distinct from the `XpIncreaseMultiplier` `EStat` the plugin was already reading. Fix: plugin now reads `PlayerXp.maxXpMultiplier` and includes it on every `player_stats_snapshot` event (`plugin/Events.cs`, `plugin/Plugin.cs`, `plugin/SimpleJson.cs`); dashboard persists it (`player_stats_history.max_xp_multiplier`, migration in `db.py`) and both the live view (`templates/index.html`) and run-history page (`templates/run_detail.html`) now flag the `XpIncreaseMultiplier` row with "(capped at X.Xx)" once the raw value exceeds the real cap. Deployed together with #gap-013's bundle once Megabonk was closed.  #gap-015

## Dashboard restart duplicated completed runs (2026-08-19/2026-08-20)

- [x] Every dashboard restart re-created a full duplicate `runs` row (with all child data - picks, damage_history, weapon_stats_history, etc.) for whatever run was most recently completed, discovered when runs 64/65/66 all showed identical `duration_seconds`/`total_damage`/pick counts despite different `started_at`/`ended_at` timestamps  [dashboard] — root cause: `tracker.py: tail_events_loop()` always started `last_size = 0` on every process start, and the plugin's `live_events.ndjson` file is never truncated except by a fresh in-game run (`ResetForNewRun`) - so any dashboard restart re-read the *entire* file from byte 0, replaying the same `run_started`→`run_ended` sequence for a run that was already durably saved to the DB on the previous process's lifetime, creating a fresh duplicate row every time. This had been happening silently across every restart tonight (multiple, for #gap-013/#gap-015/#gap-016 deploys) but only became visible once three restarts happened in a row against the same completed run. Fix: `tail_events_loop()` now seeks to the file's current end-of-file size at startup instead of 0, so only genuinely new lines written after the dashboard starts are ever processed - a run still mid-flight during a restart is not recovered into the live view (a smaller, separate concern), but no run is ever re-ingested from disk. Cleaned up the two duplicate rows (65, 66) via the same manual multi-table delete used for #gap-012. This is almost certainly the same root cause as the older, previously-unexplained #gap-006 (runs 14/15 and 24/25 - identical sequential-pair duplicates, consistent with a dashboard restart happening right after each of those runs completed) - closing #gap-006 under this fix rather than re-investigating separately, since the mechanism fully explains that pattern too.  #gap-017 (closes #gap-006)
